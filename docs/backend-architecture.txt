1 АРХИТЕКТУРА
==============================================================================

Слоистая архитектура: Controllers -> Services -> Repositories -> Models
  Controllers   принимают запрос (DTO), берут id пользователя, вызывают сервис
  Services      вся логика и проверки прав; сохраняют изменения
  Repositories  только запросы к БД
  Models        таблицы БД
  Dtos          вход выход

Проекты: Api и Worker ссылаются на Core

В MVP все команды используют одного общего Telegram-бота. Его токен задаётся
в конфигурации сервиса и не хранится отдельно для каждой команды.
Telegram-чаты привязываются непосредственно к командам. Для привязки
администратор получает одноразовый код с ограниченным сроком действия.

Worker обрабатывает обновления общего бота и связывает чат с командой.
Позиция чтения обновлений общая для бота и сохраняется в базе данных.
Отправка во все чаты команды выполняется через общий интерфейс канала.

4 ПОДКЛЮЧЕНИЕ И ДОСТАВКА В TELEGRAM
==============================================================================

  1. Администратор команды создаёт одноразовый код привязки. В базе хранится
     только его хеш и срок действия; ссылка содержит исходный код.
  2. Администратор добавляет общего бота в чат и передаёт ему код привязки.
  3. Worker получает обновление, проверяет код и его срок действия, привязывает
     чат к команде и помечает код использованным. Эти изменения и позиция
     чтения обновлений сохраняются согласованно, чтобы после сбоя обновление
     можно было обработать повторно без повторной привязки.
  4. Планировщик создаёт запись Delivery для каждого чата команды. Отправщик
     использует общий токен бота и адрес чата для доставки сообщения.

  Токен бота хранится в конфигурации сервиса, не передаётся пользователям и
  не сохраняется в записях команд или чатов. При запуске нескольких экземпляров
  Worker приём обновлений общего бота должен выполняться согласованно.
